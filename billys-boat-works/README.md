# BillysBoatWorks

The operating system for recreational rental franchises, built natively on the Kinetic Platform.
Water recreation is the initial market; the model is **recreational assets and reservations**, so
snowmobiles, ice houses, ATVs and ski equipment are a category addition, not a rewrite.

**Kapp:** `billys` · **Server:** ai-labs.kinopsdev.io · **Served at:** `/billys/` on the :3011 launcher

## Three audiences, three experiences

| Page | Audience | What it is |
|---|---|---|
| `index.html` | Consumer | Marketplace — destination search, availability, transparent pricing, protection, waiver, checkout, my trips |
| `ops.html` | Franchise operator | Operations console — action queue, fleet board, reservations, mobile check-in/return, asset economics, maintenance, damage, advisor |
| `corporate.html` | Corporate | Network management — performance ranking, attention list, franchise development pipeline, territories, safety & claims, financials |

Each page is standalone HTML with inline CSS/JS (no build step, no npm), served by the base
launcher which injects the Kinetic session.

## Architecture

Business records, workflow state, user experience and integration logic are kept separate:

- **Records** — 28 forms in `app.json`, generated by `build-app-json.mjs`
- **Reservation lifecycle** — a `Status` field driving the state machine, with a separate
  `Exception` field so exceptions (weather, no-show, damage hold) never destroy lifecycle history
- **API** — `server.mjs` exposes three namespaces (`/api/bbw/market/*`, `/ops/*`, `/corp/*`) plus
  global `/api/bbw/search`; the browser never reads more than 25 rows per request
- **Integrations** — payments, insurance, weather and notifications are modelled as
  provider-agnostic records (`Provider`, `Provider Reference`, `Source`, `Channel`) so no vendor
  is baked into the domain

### Why the index set looks the way it does

`build-app-json.mjs` declares each form's `filters` — the fields a console can AND together — and
emits an index for **every combination**. Kinetic matches an index whose parts are exactly the
queried field set, so single-field indexes are not enough: two filters that share no compound index
return a 400 at runtime even though each works alone. 28 forms → 432 indexes.

## Data model

Network: `destinations` · `territories` · `franchises` · `franchise-prospects` · `locations` · `employees`
Fleet: `equipment-categories` · `assets` (serialized) · `inventory` (quantity-tracked)
Commerce: `customers` · `reservations` · `reservation-items` · `pricing-rules` · `payments` · `protection-plans`
Operations: `waivers` · `maintenance-orders` · `inspections` · `damage-reports` · `incidents` · `claims` · `reviews` · `weather-events`
Program: `training-courses` · `training-records` · `notifications` · `royalty-statements` · `audit-log`

Serialized vs quantity tracking is a property of the **category** (`Tracking Mode`), not a separate
subsystem — a pontoon and a life jacket are both rentable inventory.

## Money is traceable

Every reservation total decomposes into `reservation-items` lines. Every captured payment carries
its royalty, marketing and processing split, and `royalty-statements` roll those up per franchise
per period. The consumer sees the same ladder before paying — base rate, weekend premium, seasonal
adjustment, accessories, protection, fees, tax.

## Scripts

```bash
node build-app-json.mjs                  # regenerate app.json from the model definition
node gen-seed.mjs                        # regenerate seed-data.json (deterministic)
node install.mjs [--seed]                # create kapp, forms, indexes, optionally seed
node reconcile.mjs [form] [--dry] [--prune]
```

`reconcile.mjs` diffs the live space against `seed-data.json` by each form's business-key field:
PUTs drifted records, POSTs missing ones. **`--prune` also deletes live records whose key is not in
the seed file** — that restores pristine demo state, and it will remove anything created through
the UI since the last seed. Omit `--prune` for a non-destructive sync.

Set `KINETIC_URL` / `KINETIC_USER` / `KINETIC_PASS`; they default to first.kinetics.com.

## What is modelled but not yet automated

Reservation lifecycle transitions, notification dispatch and claim routing are currently driven by
the API layer and the operations UI, and every state change writes to `audit-log`. Moving those
transitions onto Kinetic workflow trees is the natural next step — the records and the state
machine are already shaped for it. Weather never cancels anything automatically: an event records a
`Recommended Action` and waits for `Decision By` / `Action Taken`.

## Workflows (Kinetic Task Engine)

Four trees run in the engine, not in the web tier. Source XML in `workflows/`, deployed with
`workflows/deploy.mjs` which validates, converts treeXml to treeJson, PUTs via the **Task API**
(the Core-API treeXml PUT returns 200 but stores zero nodes) and refuses to report success unless
the stored node and connector counts match what was sent.

| Tree | Form / event | What it does |
|---|---|---|
| **Damage Response** | `damage-reports` / Submission Submitted | Operational or unsafe damage pulls the hull from the fleet, opens a blocking Damage Repair work order, writes the audit row, and escalates unsafe damage to corporate |
| **Booking Intake** | `reservations` / Submission Submitted | Queues the booking confirmation, chases an unsigned waiver by SMS, audits the booking |
| **Weather Operations** | `weather-events` / Submission Submitted | Alerts the operator when conditions warrant pausing or stopping rentals, records the assessment — and **never cancels a reservation**; the event waits for a named human decision |
| **Incident Escalation** | `incidents` / Submission Submitted | Serious and critical incidents escalate to corporate risk and are flagged for review; all incidents audited |

```bash
cd workflows
node deploy.mjs <form> <tree.xml> "<workflow name>" "Submission Submitted"
```

Validate first — the gate script is the sanctioned path:

```bash
node ../../../skills/skills/concepts/workflow-xml/scripts/validate-workflow.mjs --tree workflows/damage-response.xml
```

### Division of responsibility

The operations UI files the *record*; the engine owns the *consequences*. The browser no longer
pulls hulls from service or opens work orders on a damaged return — doing both would double-create.
Anything the engine changes is written to `audit-log` under a `*-workflow` actor.

### Not yet automated

`smtp_email_send_v1` has **no `server` property configured** on this engine, and per the workflow
skill an unconfigured SMTP server raises `UnknownVariableError` and stalls the run even with
`error_handling: Error Message`. So the trees *queue* `notifications` records rather than sending
mail. Configure that handler property and a dispatch tree becomes straightforward.

Month-end royalty close is still computed in the API layer rather than by a scheduled routine.
