# Data Model

Kapp `corporate-brain`, 12 forms. The only source of truth is `model.mjs`; `node model.mjs` regenerates `app.json`.

**Conventions**
- Every form has a stable `<Entity> ID`, uniquely indexed and generated by `newId(form)` as `PREFIX-` plus 10 uppercase hex characters.
- Kinetic supplies `createdAt`, `createdBy`, `updatedAt` and `updatedBy`. The submission `id` is used for edits, the stable ID for references.
- All fields are text. **List fields hold JSON arrays** (`["SR-…","SR-…"]`). They are written by `listValue()` and read by `parseList()`, which also accepts comma-separated text.
- Cross-record references always use stable IDs, never display names.
- Provenance fields: `Record Status` (`active`, plus `deleted`, `merged` and `test` used by code and tests), `Source IDs` (JSON list) and `Created Via` (`user`, `agent` or `connector`).

## Forms and fields

**companies**
- `Company ID`*, `Name`*
- `Name Key`: normalized name for prefix search (`nameKey()` strips legal suffixes, accents and punctuation)
- `Aliases`, `Domain`, `Industry`, `Country`
- `Customer Status`: `Unknown` / `Prospect` / `Customer` / `Former Customer` / `Partner` / `Vendor` / `Internal`. Defaults to `Unknown`.
- `Customer Status Basis`: required by the API whenever the status changes
- `First Known Date`, `Description`, `Merged Into`, plus the provenance fields

**people**
- `Person ID`*, `Full Name`*, `Name Key`
- `Email`: lowercased, used for resolution
- `Primary Company ID`, `Title`
- `Kinetic Relationship`: Customer contact, Employee, …
- `Description`, `Merged Into`, plus the provenance fields

**relationships**
- `Relationship ID`*, `From Type`, `From ID`*, `To Type`, `To ID`*, `Relationship Type`*
- `Role`, `Start Date`, `End Date`, `Date Precision`, `Notes`, plus the provenance fields
- Types in use:
  - `associated-with`: person → company, created by `resolvePerson`
  - `contact-for`: person → company
  - `involved-in`: person → project
  - `uses-product`: company → product
  - `evidence-for`: source → company, created by ingestion
- `services.link()` is idempotent: it checks From ID + type, then To ID, and merges `Source IDs`.

**communications**
- `Communication ID`*
- `Channel`: email / meeting / call / chat / letter / other
- `Subject`, `Communication Date`
- `Participants`: JSON list of `{name,email,role}`
- `Company ID`, `Company IDs`, `Person IDs`
- `Source ID`: the evidence; the message body stays in the source system
- `Summary`, plus the provenance fields

**historical-events**
- `Event ID`*, `Title`*
- `Event Type`: first-contact / meeting / proposal / contract / implementation / commercial / support / renewal / product / organizational / other
- `Event Date`: `YYYY`, `YYYY-MM` or `YYYY-MM-DD`
- `Date Precision`: `exact` / `month` / `year` / `approximate` / `unknown`
- `Company ID`, `Project ID`, `Product ID`, `Person IDs`, `Description`
- `Verification Status`: mirrors the backing knowledge entry
- `Knowledge ID`: the backing entry
- plus the provenance fields

**decisions**
- `Decision ID`*, `Title`*, `Decision Date`, `Date Precision`, `Decision Area`
- `Context`, `Decision`, `Rationale`, `Alternatives Considered`, `Decided By`
- `Company ID`, `Project ID`, `Product ID`, `Verification Status`, plus the provenance fields
- Full CRUD exists; the pilot created none.

**knowledge-entries**
- `Knowledge ID`*, `Knowledge Type`*, `Subject Type`, `Subject ID`, `Company ID` (denormalized for queries), `Title`*, `Statement`
- `Supporting Source IDs`: JSON list
- `Extraction Method`: manual / rule-based / interview / `ai-agent (…)` / `ai-generative (…)`
- `Model Confidence`: informational only
- `Review Status`, `Verified By`, `Verified At`, `Superseded By`, `Supersedes`
- `Contradicts`: JSON list
- `Review History`: JSON list of `{at, by, actorType, action, from, to, comment}`
- `Job ID`, `Last Reviewed At`, `Record Status`, `Created Via`

**sources**
- `Source ID`*: `SR-` plus 20 hex characters of `sha256(system \0 originalId)`
- `Source Type`: email, document, presentation, spreadsheet, folder, code, record, interview, notes
- `Source System`*: `gmail` / `google-drive` / `github` / `kinetic` / `manual`
- `Original ID`*, `Title`, `Source Date`, `Owner`
- `Access Scope`: `internal` / `restricted`
- `Original URL`
- `Excerpt`: at most 4000 characters; manual notes store their content here
- `Content Hash`
- `Processing Status`: retrieved / extracted / changed / source-deleted / permission-restricted / failed
- `Company ID`, `Company IDs`, `Person IDs`, `Ingest Job ID`, `Last Synced At`, `Processing Error`, `Record Status`, `Created Via`

**projects**
- `Project ID`*, `Name`*, `Name Key`, `Company ID`, `Project Type`
- `Project Status`: Planned / Active / Completed / Cancelled / Unknown
- `Start Date`, `End Date`, `Date Precision`, `Product IDs`, `Description`, plus the provenance fields

**products**
- `Product ID`*, `Name`*, `Name Key`, `Category`, `Introduced Date`, `Product Status`, `Description`, plus the provenance fields
- Only admins can write through the API.

**research-jobs**
- `Job ID`*, `Title`*
- `Job Type`: ingestion / research
- `Connector`
- `Scope`: JSON
- `Subject Type`, `Subject ID`
- `Status`: queued / running / paused / completed / failed / blocked / cancelled
- `Checkpoint`: JSON
- `Batch Size`: 25 or fewer
- `Items Discovered`, `Items Processed`, `Items Skipped`, `Items Failed`
- `Errors`: JSON, last 25
- `Requested By`, `Started At`, `Completed At`, `Summary`
- `Open Questions`: JSON
- `Attempts`, `Record Status`, `Created Via`

**audit-log** (append-only)
- `Audit ID`*, `Action`*
- `Entity Type`, `Entity ID`
- `Actor`, `Actor Type`: user / agent / connector / workflow
- `From Status`, `To Status`, `Comment`
- `Details`: JSON, at most 4000 characters
- `Occurred At`

(* = required)

## Indexes
`deploy.mjs` merges these with existing definitions plus the system indexes (`createdBy`, `updatedBy`, `submittedBy`, `closedBy`, and unique `handle`).

| companies | Company ID | Record Status, Customer Status, Name Key, Name | [Record Status, Name Key], [Customer Status, Name Key] | prefix search, status filter, resolution |
| people | Person ID | Record Status, Name Key, Primary Company ID, Email | [Primary Company ID, Name Key], [Record Status, Name Key] | company contacts, email resolution |
| relationships | Relationship ID | From ID, To ID, Relationship Type, Record Status | [From ID, Relationship Type], [To ID, Relationship Type] | `link()` dedupe, `linksOf()` |
| communications | Communication ID | Company ID, Source ID, Communication Date, Record Status | [Company ID, Communication Date] | dossiers, person profile |
| historical-events | Event ID | Company ID, Event Date, Event Type, Verification Status, Project ID, Product ID, Record Status, Knowledge ID | [Company ID, Event Date], [Event Type, Event Date], [Record Status, Event Date], [Project ID, Event Date], [Product ID, Event Date] | timeline (range + orderBy), review sync by Knowledge ID |
| decisions | Decision ID | Company ID, Decision Date, Verification Status, Record Status, Product ID | [Record Status, Decision Date] | dossiers |
| knowledge-entries | Knowledge ID | Review Status, Knowledge Type, Subject ID, Company ID, Job ID, Record Status | [Subject ID, Review Status], [Company ID, Review Status], [Knowledge Type, Review Status], [Company ID, Knowledge Type], [Company ID, Knowledge Type, Review Status] | review queue, knowledge explorer filters, stats |
| sources | Source ID | Company ID, Source System, Processing Status, Ingest Job ID, Source Date, Record Status | [Company ID, Source Date], [Source System, Processing Status], [Source System, Original ID] | dedupe (unique Source ID), source filters, job detail |
| projects | Project ID | Company ID, Record Status, Name Key, Project Status | [Company ID, Start Date] | prefix search, dossiers |
| products | Product ID | Record Status, Name Key, Category | — | prefix search |
| research-jobs | Job ID | Status, Job Type, Subject ID, Connector, Record Status | [Status, Job Type] | jobs list |
| audit-log | Audit ID | Entity ID, Action, Actor, Occurred At | [Entity ID, Occurred At] | audit trail on knowledge detail |

Kinetic unique indexes are **case-insensitive**, while Drive, Gmail and GitHub IDs are case-sensitive. That is why deduplication uses the hashed `Source ID`; `[Source System, Original ID]` is a plain lookup index, not a unique one.

## Truth model (`lib/core.mjs`)
- **Evidence:** `sources`, including manual interviews and recollections.
- **Knowledge:** `knowledge-entries` with `Knowledge Type` ∈ `fact`, `interpretation`, `narrative`, `lesson`, `claim`, `recollection`, `summary`.
- **Review statuses:** `proposed`, `verified`, `disputed`, `rejected`, `superseded`, `needs-research`.
- **New entries:** `newKnowledgeValues()` always creates entries as `proposed`, whoever creates them, and records the first `Review History` row.

| From \ action → to | allowed targets |
|---|---|
| proposed | verified, rejected, disputed, needs-research, superseded |
| needs-research | proposed, verified, rejected, disputed, superseded |
| disputed | verified, rejected, needs-research, superseded, proposed |
| verified | disputed, superseded |
| rejected | proposed |
| superseded | — |

Actions map to statuses as follows: `approve`→verified, `reject`→rejected, `dispute`→disputed, `research`→needs-research, `supersede`→superseded, `reopen`→proposed.

Rules enforced by `reviewTransition()`:
- A named reviewer is required.
- **Only `actorType: "user"` can verify.** Agents and connectors may propose, dispute or request research, but never verify.
- `fact`, `narrative`, `lesson`, `summary` and `interpretation` need at least one supporting source to be verified. `claim` and `recollection` do not.
- Reject, dispute and research require a comment. Supersede requires the replacing Knowledge ID.
- Moving away from `verified` clears `Verified By` and `Verified At`.
- `Model Confidence` never affects status.

Contradictions are linked both ways (`linkContradiction`). Neither entry is overwritten, and the Contradiction Review workflow marks the new one `disputed`.

**Events** follow their backing knowledge: a review updates `Verification Status` on every event with that `Knowledge ID`. The API refuses (409) changes to the title, date, precision, description or company of a verified event. Record new information as a new event or knowledge entry and supersede the old one.

**Date precision:** dates parsed from a title are `exact`, `month` or `year`, exactly as written. Dates taken from a file's creation time in its system are always `approximate`, and no date at all gives `unknown`. The UI shows ≈ and a precision pill.
